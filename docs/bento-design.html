お弁当注文Bot ― Discord だけで完結する注文と集金

アルムナイの弁当注文を、Webサイトを一切開かずに Discord のメッセージ1枚で完結させる。この資料は「何を作るか」と「なぜその形なのか」を、Discord Bot を書いたことがない人にも分かるようにまとめたもの。

2026-09-02 Cloudflare Workers / D1 認証なし・ストレージなし・無料枠

00この資料の結論

  1. 作るのは「1枚の生きたメッセージ」。 Discord のチャンネルに貼られたメッセージが、注文が入るたびに自動で書き換わる。誰も Web サイトを開かない。ログインもしない。
  2. Googleフォームに勝てるのはこの一点だけ。 フォームは回答したあと結果が見えない。この Bot は、スクロールしただけで「誰が何を頼んだか」「誰がまだ払っていないか」が全員に見える。
  3. 作らないものを、作るものと同じだけ決めた。 認証・Webページ・メニュー登録・締切の自動判定・権限管理・AI。全部いらないと結論した。残ったのは Discord からの通信を受ける API 1本と、テーブル3つ。

この資料は設計の合意事項をまとめたもの。実装手順の詳細は同リポジトリの grill-bento-order-20260902.md に置いてある。

01完成形

製品のすべてが、この1枚のメッセージに収まっている。画面遷移も、ログイン画面も、マイページも存在しない。

幹事が /bento と打つと、チャンネルにこのメッセージが投稿される。あとは全員がボタンを押すだけ。

📌 9/15(月) お弁当 📎 メニュー: https://tenpo.example.com/bento 🍱 唐揚げ弁当 ¥650 ×3 gaku, taro, hana 🍱 のり弁 ¥480 ×2 jiro, saki 🍱 幕の内 ¥820 ×1 kenta ──────────────────────────────── 弁当代 ¥4,310 [ 頼む ▼ ] [ 取り消す ▼ ] [ 新しく入力 ] [ メニューを変える ] [ 締め切る ]

図1: 注文フェーズの集計メッセージ。誰かが注文するたびに Bot がこのメッセージ自体を書き換える（新しいメッセージを投稿するのではない）。

メニューのURLは /bento の任意引数でも渡せるが、Discord のコマンド入力欄では任意引数の存在に気づきにくい。そこで集計メッセージ側にも [ メニューを貼る ] を置いた。未設定なら「貼る」、設定済みなら「変える」と表示が変わるので、ボタンの文字自体が「メニューを付けられる」という説明になっている。

幹事が [ 締め切る ] を押すと、みんなで割る費用と支払先を入力する小さな入力欄が開く。そこで金額が確定し、メッセージが集金モードに切り替わる。支払先は自由文字列で、PayPayの電話番号でも送金リンクでも振込先の口座でもよい。同じサーバーで前回使った値が初期値に入る。

📌 9/15(月) お弁当 🍱 唐揚げ弁当 ¥650 + ¥84 = ¥734 ×3 gaku, taro, hana 🍱 のり弁 ¥480 + ¥84 = ¥564 ×2 jiro, saki 🍱 幕の内 ¥820 + ¥84 = ¥904 ×1 kenta ──────────────────────────────── 弁当代 ¥4,310 ＋ 配送料 ¥500 = ¥4,810 配送料は6人で均等割 → ¥84（端数切り上げ・余り¥4は幹事） 💰 集金 4/6 未払い: jiro, saki 💳 支払先 PayPay 090-1234-5678 〇〇銀行 △△支店 普通 1234567 ヤマダタロウ [ 支払った ] [ 未払いに戻す ▼ ] [ 再開 ]

図2: 集金フェーズ。配送料は均等割だが、弁当の値段が違うので各自の支払額は全員バラバラ。だから行ごとに実際に送る金額を書く。暗算させない。

02なぜ Googleフォームではないのか

同じ機能はフォームで15分で作れる。だから「フォームに構造的にできないこと」を1つ選んで、そこに全部を賭けた。

弁当の幹事が実際に面倒なのは、次の4つ。

表1: 幹事の手間と、フォームで解けるかどうか
面倒なことフォームで解けるかこの Bot はどうするか
注文の取りまとめ
（「私A弁当」がチャットに散らばる）		解ける同じく解ける（差はつかない）
店に出す最終オーダー
（「A弁当7個、B弁当3個」の形にする）		半分。スプレッドシートで手集計常に集計済みの状態で表示されている
集金の追い込み
（未払いを一人ずつ追いかける）		解けない未払いが全員に見えている
結果を全員に見せる解けない（回答後は自分の分すら見えない）チャンネルを見れば常に最新

勝ち筋は下2つ。とくに「未払いが全員に見えている」は、幹事が一番やりたくない仕事（人にお金の催促をする）を、機械の状態表示に置き換えるという意味を持つ。ここがこの道具の存在理由。

ただし、未払い者に @メンション で通知は飛ばさない。通知を飛ばすと「取り立て」になって角が立つ。見れば分かるが、鳴らない。この強度が最適だと判断した。

03ログインしないのに、なぜ「誰が」が分かるのか

Discord が本人確認を代行してくれている。だから認証を自分で作る必要がない。

ここが初めて Discord Bot を作る人が一番不思議に思うところなので、先に説明する。

誰かが Discord でボタンを押すと、Discord のサーバーから自分のサーバー（Cloudflare Workers）に HTTPリクエストが飛んでくる。その中身には、押した人の Discord ユーザーID と表示名が最初から入っている。

{
  "type": 3,
  "member": {
    "user": { "id": "123456789012345678", "username": "gaku" }
  },
  "data": { "custom_id": "order_select", "values": ["唐揚げ弁当"] }
}

しかもこのリクエストには Discord の電子署名がついている。署名を検証すれば「本当に Discord から来たリクエストだ」と確認できるので、他人がユーザーIDを詐称して直接 API を叩くことはできない。

つまり、ログイン画面もパスワードもセッションも作らずに、本人確認が完了している。「認証基盤なし」という制約は、この設計では制約ではなく前提条件になっている。

むしろ「名前を手で入力してもらう」設計にすると、表記ゆれ（gaku / Gaku / がく）が起きて劣化する。Discord のユーザーIDは絶対に一意で、絶対に詐称できない。使わない手はない。

04全体の仕組み

動くのは「Discordからリクエストが飛んできた瞬間」だけ。常時動きつづけるサーバーは要らない。

デプロイするのは src/index.ts ただ1ファイルの Worker。ブラウザで開く画面は作らない。ルーティングも要らないので、フレームワークも入れない。

データベースが外から見えないことが、この構成の一番効いている点。D1 には URL も API キーも無く、wrangler.jsonc で紐づけた Worker から env.DB 経由でしか触れない。つまり署名検証を通らないリクエストは、そもそもデータベースに到達する経路を持たない。公開 API を持つデータベースだと、この「署名を迂回されない」を設定で守り続ける必要がある。

初学者がハマる3点。（1）Discord は3秒以内に返事がないとタイムアウトするので、まず「考え中」を即返してから処理する。（2）署名検証には加工前の生の本文が要るので、req.json() より先に req.text() を呼ぶ。（3）D1 はローカル（--local）とリモート（--remote）で中身が別物。手元で通ったからといって本番のテーブルはできていない。

表2: ボタンの一覧と権限
ボタン押せる人動き

権限チェックのコードは1行も書かない。アルムナイの内輪で悪用される想定がないので、誰が誰の注文を消せてもいい。この判断ひとつで「幹事とは誰か」を管理する仕組みが丸ごと不要になった。

06メニューを登録しないという判断

幹事にメニューを入力させない。注文が積み上がると、選択肢が勝手に増えていく。

頼む店は毎回違う。だから幹事に毎回メニューを打ち込ませると、2回目で道具が捨てられる。かといって全員が自由テキストで書くと「唐揚げ弁当 / からあげ弁当 / 唐揚げ」が混ざって、店に出す発注が作れない。

解決策は、誰かが入力した品が、そのまま次の人の選択肢になること。

19:00 幹事が /bento を叩いた直後 まだ注文がありません [ 新しく入力 ] ← 選択肢が空なので「頼む ▼」は出ない 19:05 gaku が [新しく入力] → 「唐揚げ弁当 / 650」 🍱 唐揚げ弁当 ¥650 ×1 gaku [ 頼む ▼ ] ← 唐揚げ弁当 ¥650 が選択肢として生まれた [ 新しく入力 ] 19:07 taro も唐揚げ弁当。[頼む ▼] を開くともう入っている 🍱 唐揚げ弁当 ¥650 ×2 gaku, taro taro は一文字も打っていない 19:10 hana はのり弁。まだ無いので [新しく入力] 🍱 唐揚げ弁当 ¥650 ×2 gaku, taro 🍱 のり弁 ¥480 ×1 hana [ 頼む ▼ ] ← 選択肢が2つになった

図5: 6人なら手入力は2〜3回。残りは全部タップで終わる。

表記ゆれが起きない理由は単純で、打つより押すほうが明らかに楽だから。すでにある品をわざわざ打ち直す人はいない。名寄せ処理も入力検証もAIも要らない。

データベース側でも、メニュー用のテーブルを作らない。選択肢は注文テーブルから重複を除いて取り出すだけ。

select distinct item_name, price
from bento_orders
where event_id = $1;

07お金の計算

配送料は全員で均等に割る。ただし弁当の値段が違うので、各自が送る金額は全員バラバラになる。

表3: 6人・配送料¥500 の場合の計算（¥500 ÷ 6人 = ¥83.33 → 切り上げて ¥84）
品弁当代配送料の割前送る金額人数
唐揚げ弁当¥650+¥84¥7343
のり弁¥480+¥84¥5642
幕の内¥820+¥84¥9041
合計¥4,310+¥504¥4,8146

決めたルールは3つ。

  • 均等割にする（弁当代に比例させない）。配送は個数ではなく1回の配達に対してかかる費用なので、人数で割るのが自然
  • 端数は切り上げる。¥83.33 を切り捨てると集金が足りなくなって幹事が持ち出しになる。切り上げれば ¥4 余るだけで済む（余りは幹事の取り分）
  • 金額の入力チェックはしない。¥820 を ¥8,200 と打っても、集計メッセージに大きく出るので人間が必ず気づく。上限を決め打つと、高い弁当や2人分まとめる場合が弾かれてそちらの害が大きい

この「みんなで割る費用」の欄は配送料専用ではなく、複数行で 配送料 500 API代 300 のように何個でも入れられる。均等割のロジックは同じものを使い回せるので、実装は増えない。

08データの持ち方

テーブルは3つだけ。1人1個という仕様を、アプリのコードではなくデータベースの制約で保証する。

create table bento_events (
  id           text primary key,
  guild_id     text not null,
  channel_id   text not null,
  message_id   text,                     -- 書き換える対象のメッセージ
  title        text not null,
  menu_url     text,
  status       text not null default 'open' check (status in ('open', 'closed')),
  shared_costs text not null default '[]',  -- JSON: [{"label":"配送料","amount":500}]
  payment_info text,                        -- 締め切るときに入れる送金先。自由文字列
  created_at   text not null default (datetime('now'))
);

create table bento_orders (
  id              text primary key,
  event_id        text not null references bento_events(id) on delete cascade,
  discord_user_id text not null,
  display_name    text not null,
  item_name       text not null,
  price           integer not null,
  paid            integer not null default 0,  -- SQLite に boolean は無い。0/1
  created_at      text not null default (datetime('now')),
  unique (event_id, discord_user_id)           -- ← 1人1個をここで担保する
);

create index idx_bento_orders_event on bento_orders (event_id);

D1 の中身は SQLite なので、PostgreSQL の書き方はそのまま通らない。型は少なく、uuid も boolean も jsonb も無い。ID は crypto.randomUUID() でアプリ側が作って text に入れ、真偽値は 0 / 1、JSON は文字列で持って読むときに JSON.parse する。日時も文字列。

最後の unique (event_id, discord_user_id) が効いている。同じ人が2回注文しようとするとデータベースが拒否するので、「すでに注文済みかどうか」を毎回コードで確認する必要がない。二重注文というバグが構造的に起きなくなる。

message_id は、書き換える対象のメッセージを覚えておくためのもの。これがないと、次に誰かが注文したときにどのメッセージを更新すればいいか分からなくなる。

09作らないと決めたもの

短い期間で仕上げるために削ったのではなく、あったほうが悪くなるから削った。

表4: 検討して落とした機能と、その理由
落としたもの理由
ログイン・認証Discord が本人確認を済ませてくれている（→ 03）
Webページ開かせた時点で「Discordで完結」が崩れる。デプロイするのは Worker 1本だけ
数量（1人で2個）アルムナイの弁当では起きない。入れると入力欄・検算・割り勘の計算が全部増える
締切時刻の自動判定幹事が「締め切っていい？」と聞いて締めるので、機械が時刻を知る必要がない。日時のパース（「明日の21時」をどう読むか）という事故りやすい処理が丸ごと消えた
定期実行（cron）とリマインド締切を手動にしたので不要。Cron Triggers も時刻パースも書かずに済んだ
締切後の変更・キャンセル例外は扱わない。締め切ったらボタンが切り替わるだけ
権限管理・幹事という概念内輪で悪用されない前提。権限チェックのコードがゼロになった
メニュー登録機能注文がそのままメニューになる（→ 06）
AI / LLM の組み込みこの課題の「AI活用」はAIを使って開発することを指す。動くシステムの中で LLM を呼ぶ場所はない

10用語

スラッシュコマンド
Discord のメッセージ欄で / から始めて呼び出すコマンド。この Bot では幹事が使う /bento だけ。
インタラクション (Interaction)
ユーザーがコマンドを打ったりボタンを押したりしたときに、Discord から自分のサーバーへ飛んでくる HTTPリクエストのこと。この Bot が受け取るのはこれだけ。
Interactions Endpoint URL
そのリクエストの届け先として Discord 側に登録する URL。ここでは https://bento.<自分の名前>.workers.dev/。登録時に Discord が疎通確認をしてくるので、署名検証を実装するまで登録できない。
モーダル (Modal)
ボタンを押すと開く入力用の小窓。テキスト欄が最大5つまで置ける（日付を選ぶカレンダーのような部品は存在しない）。この Bot では「品名と金額」「配送料」の入力に使う。
セレクトメニュー (Select Menu)
プルダウンで選ぶ部品。選択肢は25件まで。[ 頼む ▼ ] がこれ。
Embed
Discord のメッセージをきれいに整形して表示するための構造。図1・図2の見た目はこれで作る。
Ed25519 署名
Discord が「このリクエストは確かに Discord が送った」ことを証明するためにつける電子署名。Workers のランタイムに入っている crypto.subtle が Ed25519 に対応しているので、追加のライブラリは要らない。
Worker
Cloudflare 上で動く、リクエストが来たときだけ起動する関数。src/index.ts に fetch を書くだけ。サーバーの常時起動も、待機中の課金も無い。
D1
Cloudflare の SQLite データベース。外向きの URL も API キーも無く、wrangler.jsonc で紐づけた Worker から env.DB 経由でしか触れない。この「外から触れない」が、そのままセキュリティ設計になっている。
バインディング (binding)
Worker に D1 などの資源を結びつける設定。wrangler.jsonc に書くと、コードから env.DB という名前で使えるようになる。接続文字列やパスワードを環境変数に置く必要がない。
