お弁当注文Bot の構成 ― 何を使って、どうつながっているか

動いている Bot が、どの部品でできていて、部品同士がどの順番で呼び合っているのかを一枚で見渡せるようにした資料。Cloudflare も Discord Bot も触ったことがない人を読み手に想定している。「何を作るか・なぜその形にしたか」は docs/bento-design.html にあるので、ここでは仕組みだけを扱う。

2026-09-04 Cloudflare Workers / D1 自分で書くコードは1ファイル

00この資料の要点

  1. 部品は4つしかない。 Discord、Cloudflare Workers、Cloudflare D1、そしてリポジトリのコード。このうち自分で用意して運用するのは Workers と D1 の2つだけで、書いたコードは src/index.ts の1本に収まっている。
  2. 画面を作っていない。 用意したのは Discord のメッセージ1枚だけで、フロントエンドも Web サーバーも管理画面も持たずに済ませている。利用者が見て触るのは Discord のメッセージとそこに並ぶボタンそのもので、このアプリはその本文を書き換えているだけである。
  3. つながりは一方通行。 Discord が Worker を叩き、Worker が D1 を読み書きして、その結果を Discord へ返す。逆向きの経路は、この Worker を通る1本きりに絞ってある。
  4. 読む順番。 図1で全体を掴み、02〜03で部品をひとつずつ見て、04でボタン1回ぶんの流れを追う。手を動かす段になったら07のファイル対応表から入るとよい。

01登場人物は4つだけ

端末からデータベースまで通して見ても、自分で立てて面倒を見るサーバーが1台も無い。

ふつうの Web サービスを作ろうとすると、画面を描くフロントエンド、リクエストを受け付ける Web サーバー、データを置くデータベース、そしてそれらを載せるサーバーやコンテナが要る。この Bot にあるのは Discord と Cloudflare という2社のサービスだけで、間をつなぐために自分で書いたコードは1ファイルに収まる。

なぜここまで減らせるのか？ 理由は、画面をまるごと Discord に任せているところにある。注文の一覧も、押すボタンも、入力フォームも、Discord がすでに持っている部品を組み合わせて出している。こちらが用意するのは「いま注文が何件あるか」を答える処理だけで済む。

表1: 使っているものと、その役割
名前何をするふつうなら代わりに置くもの
Discord画面・ボタン・入力フォーム・ログイン済みのユーザー情報を提供するReact などのフロントエンドと、ログイン機能
Cloudflare WorkersDiscord から届いた1本の POST を処理して、返す本文を組み立てるEC2 や Render に常駐させた Node.js の Web サーバー

ランタイムの依存パッケージはゼロ。package.json に入っているのは wrangler・TypeScript・Biome の3つで、いずれも開発用で、本番の Worker に載るのは自分のコードだけである。

02Cloudflare Workers ― 呼ばれたときだけ起きる

Worker は待機し続けるプロセスではなく、リクエストが届いた瞬間に起きて返事を書いたら消える関数である。

サーバーと聞いて多くの人が思い浮かべるのは、電源を入れっぱなしにしてリクエストを待っている機械だろう。Workers はそれとはまったく別の形をとる。コードを置いておくと、Cloudflare が世界中のデータセンターにそれを配り、リクエストが来た地点で必要なぶんだけ実行する。誰も注文しない日には何も起きないまま過ぎるので、費用も0円で済む。

表2: 常駐サーバーとの違い
観点一般的なサーバー（VPS / EC2）Cloudflare Workers
動いている時間常時。夜中も待機しているリクエストの処理中だけ
費用の数え方起動していた時間リクエストの回数と CPU 時間
使わない期間料金は発生し続ける0回なら0円。休止もしない
デプロイイメージを作って配置し、プロセスを入れ替えるnpm run deploy の1回
使える APINode.js のすべて（fs なども）ブラウザ寄り。fetch と crypto.subtle はあるが fs は無い

Worker の入口は export default { fetch(req, env, ctx) } という形をしていて、このアプリが受け取る POST は1種類きりで足りている。パスによる振り分けが要らないので、Express や Hono のようなルーティングのライブラリも入れていない。req.method を見て、あとは Discord が送ってきた interaction.type で分岐するだけで足りている。

署名の検証に使う Ed25519 も、外部のライブラリではなくランタイムに組み込みの crypto.subtle で処理している。npm から何かを足す前に、Workers が最初から持っていないかを確かめる癖をつけると、この構成の軽さは保たれる。

03Cloudflare D1 ― ネットワーク上に住所を持たないDB

D1 には接続文字列もパスワードも無い。設定ファイルに書いた binding を通してしか開かない。

PostgreSQL や MySQL を使ったことがあれば、postgres://user:pass@host:5432/db のような接続文字列を環境変数に入れた記憶があるはずだ。D1 にはそれが無い。wrangler.jsonc に "binding": "DB" と書いておくと、Worker のコードから env.DB という変数として現れる。渡ってくるのはネットワークの接続先ではなくオブジェクトなので、鍵が漏れるという事故がそもそも起こらない。

const rows = await env.DB.prepare(
  "select * from bento_orders where event_id = ?",
).bind(eventId).all();

値は必ず ? と .bind() で渡す。文字列を連結して SQL を組み立てると、品名に ' を含む注文が入っただけで壊れるうえ、SQL インジェクションの経路にもなる。

D1 の実体は SQLite なので、PostgreSQL の語彙はそのままでは通らない。uuid 型も boolean 型も jsonb 型も存在しないため、ID は crypto.randomUUID() の文字列を text に入れ、真偽値は 0 と 1 の整数で持ち、JSON は文字列のまま入れて読むときに JSON.parse している。

初学者がいちばん引っかかるのは、じつはここから先の落とし穴のほうだろう。ローカルの D1 と本番の D1 は完全に別物である。 npm run db:apply は手元のファイルにテーブルを作るだけなので、これだけ打って本番にアクセスすると no such table で落ちる。本番へ反映するには npm run db:apply:remote をもう一度打つ必要がある。

スキーマを変えるときは、既存のマイグレーションファイルを書き換えてはいけない。すでに適用済みのファイルを直しても、適用済みと記録されている本番では二度と実行されないからだ。npm run db:new -- 名前 で新しいファイルを足す。

04ボタンを1回押すと何が起きるか

押されるたびに全注文を読み直してメッセージを丸ごと描き直している。差分の更新はしていない。

参加者が「頼む」のプルダウンから唐揚げ弁当を選んだとしよう。そこから表示が変わるまでに、次の順番で処理が進む。

  1. Discord が Worker へ POST を送る。本文には、押した人の ID と表示名、押されたボタンの custom_id、そして Ed25519 の署名が入っている。
  2. Worker はまず await req.text() で本文を文字列のまま受け取り、署名を検証する。ここで失敗したら 401 を返して終わる。
  3. 検証を通ってから JSON.parse し、custom_id を : で割って操作の種類（pick）とイベントID を取り出す。
  4. イベントの status を D1 から引く。締め切り済みなら、ボタンが残って見えていても注文は受け付けない。判断の根拠は画面ではなく DB に置くという原則がここに出ている。
  5. 注文を insert ... on conflict do update で書き込む。同じ人の2回目は行が増えるのではなく上書きになる。
  6. そのイベントの注文を全件読み直し、render() で本文の文字列を、components() でボタンの配列を組み立てる。
  7. { type: 7 } を返す。Discord はこれを見て、押された元のメッセージを丸ごと差し替える。

注目してほしいのは6番目である。誰かの1件のために全件を読み直すのは、無駄ではないのだろうか？ この方式には「表示は必ず DB の現在値と一致する」という性質がある。差分更新にすると、更新を1回取りこぼしただけで画面と実態がずれ、しかもずれたことに誰も気づけない。数十件までの規模なら、丸ごと描き直すほうが安全で、コードもずっと短くなる。

メニューのプルダウンにも同じ考え方が効いている。品名の一覧を保持するテーブルは無く、すでに入っている注文をそのままメニューとして並べている。1人目が手で入力すると、2人目からはそれが選択肢になる。

053秒の壁が、コードの形を決めている

Discord は3秒返事が来ないと失敗表示に切り替える。この制約が2種類の応答パターンを生んでいる。

Discord の Interactions には厳しい時間制限がある。ボタンが押されてから3秒以内に何かを返さないと、押した人の画面には「アプリケーションが応答しませんでした」と出てしまう。その後にこちらが正しい結果を返しても、もう手遅れになる。

そこで、処理の重さに応じて返し方を2つ使い分けている。

ひとつめは type: 7（UPDATE_MESSAGE）。 押された元のメッセージをその場で差し替える返し方で、注文・取り消し・支払い済みの操作はすべてこれで処理している。D1 を読み書きして本文を組み立てるだけなので、3秒には余裕をもって収まる。Discord API を別途叩く必要が無いところがこの方式の効きどころで、Bot トークンすら使わずに済む。

ふたつめは type: 5（DEFERRED）。 /bento で募集を始めるときだけは、D1 への保存に加えてチャンネルへ新しいメッセージを投稿する必要があり、Discord API への往復が挟まる。そこで先に「考え中」の状態だけ返しておき、残りの処理を ctx.waitUntil() に渡している。waitUntil は、レスポンスを返したあとも Worker を終了させずに処理を続けさせるための仕組みである。

await req.text() より先に req.json() を呼んではいけない。署名の検証対象は生のボディ文字列で、一度パースしてから組み直した文字列では検証が通らなくなる。Interactions Endpoint URL の登録そのものが失敗するので、最初につまずくならたいていここになる。

06ログイン機能が無いのに、なぜ成立するのか

「誰が押したか」を Discord が署名つきで送ってくるので、このアプリは認証を自分で持つ必要がない。

注文アプリなのに、ユーザーテーブルもパスワードもセッションも持っていない。これで本当に大丈夫なのだろうか？ 成立している理由は2段ある。

1段目は署名の検証である。 Discord は各リクエストに Ed25519 の署名を付けてくる。Worker は公開鍵でそれを検証し、通らなければ 401 を返してそこで打ち切る。署名が正しいということは、そのリクエストが Discord から来たという証明であり、本文に書かれたユーザー ID も Discord が保証した値として扱える。自分でログインを実装するより、Discord のログイン結果をそのまま信じるほうが安全で短い。

2段目は、D1 に外向きの入口が無いことである。 01 の図で見たとおり、D1 に触れるのは binding を持つ Worker だけで、その Worker が公開しているのは、署名検証を通ったリクエストだけが先へ進める POST 1本きりである。つまりデータベースへ到達する経路が、検証を通った Discord からのリクエストという1本に絞られている。

この性質は、Web ページや管理用の API を1つ足した瞬間に消える。軽く便利な口を開けたくなったときは、それが上の保証を壊さないかを先に考えたほうがよい。

表3: 秘密として扱うものは2つだけ

読む順番は index.ts → migrations → wrangler.jsonc の3つで、それ以外は補助的なもの。

08あえて入れていないもの

構成の軽さは、足さなかったものの一覧のほうによく表れている。

表5: 入れなかったものと、その代わり
入れなかったもの代わりにどうしているか
Web フレームワーク（Express / Hono）受けるのは POST 1本だけなので、ルーティングそのものが要らない
認証・セッション・ユーザーテーブルDiscord が署名つきでユーザー ID を送ってくる
オブジェクトストレージ（R2 / S3）画像もファイルも扱わない
KV・Durable Objects・Queues状態はすべて D1 の2テーブルに収まっている
Cron Trigger（定期実行）締め切りは幹事がボタンで行う。自動判定を持たない
LLM の API叩く箇所が無い。品名の入力は人がそのまま書く
Discord の署名検証ライブラリランタイム内蔵の crypto.subtle で足りる
メニュー用のテーブルすでに入っている注文をそのまま選択肢として並べる

この一覧は「機能が足りない」という意味ではなく、「無くても成立すると確かめたので置かなかった」という記録になっている。何かを足したくなったときは、まずこの表に同じ発想の行が無いかを見てほしい。

09用語の対応

Interaction
スラッシュコマンド、ボタン、プルダウン、モーダルの送信をまとめた呼び方。Discord はこれらすべてを同じ URL に POST してくるので、interaction.type の数字で見分ける。
binding
Worker から外部リソースへつなぐ口を、設定ファイルで名前をつけて渡す仕組み。wrangler.jsonc に "binding": "DB" と書くと、コードでは env.DB になる。
custom_id
ボタンやプルダウンに埋め込んでおく文字列で、押されたときそのまま返ってくる。このアプリでは pick:イベントID のように操作名とイベント ID を : でつないで持たせている。
ephemeral
押した本人にだけ見える返信。エラーの通知はすべてこれで返すので、やりとりは本人の画面だけで完結する。
deferred（type 5）
「受け取ったので少し待って」とだけ先に返す応答。3秒を超えそうな処理のときに使い、残りは ctx.waitUntil() で続ける。
マイグレーション
テーブルの変更を1ファイル1手順で積み上げていく方式。適用済みの記録が DB 側に残るため、同じファイルはかならず1回だけ実行される。
